# v0.9.5 / AUD-01 — a `304` cannot pollute a shared cache entry

Date: 2026-11-09. Branch `release/v0.9.5`, HEAD `ecda55a` plus the
uncommitted working-tree changes below. Nothing was committed, pushed,
tagged, released or published.

## Objective

Close the P0-1 blocker from `docs/audit-2026-11-09/roadmap-v0.9.5.md`: a
`304` that revokes shared storability must never refresh and serve the old
body under the new policy. The entry is removed from memory and disk, the
request is resolved with an unconditional full fetch, and a second `304` to
that unconditional request is refused with `502`.

### Revocation policy

`refresh_storable` returns false, and `refresh` therefore invalidates, when
the `304` carries `Set-Cookie`, `Cache-Control: private` or `no-store`,
`Vary: *`, a `Vary` over `cookie`/`authorization`, or a `Vary` different from
the stored one. `Set-Cookie` is never merged; only the end-to-end allowlist is
merged for a clean `304`.

The invalidation calls `complete(Gone)`, so cache-lock waiters wake to
`Gone` instead of receiving a refreshed entry under revoked headers, and the
disk variant is removed. A clean `304` still returns
`RefreshOutcome::Refreshed` and keeps `X-Cache: REVALIDATED`.

## E2E journeys (real sockets, not mocks)

`cargo test -p eqproxy-net --test e2e_cache` → **20 passed, 0 failed**:

- `a_304_with_session_headers_never_pollutes_the_shared_entry` — `Set-Cookie`
  and `private` in the `304`; the next anonymous client gets a clean full
  fetch, no session header, and a later `HIT` without the poison.
- `a_304_that_changes_vary_invalidates_the_entry` — a new `Vary` removes the
  entry and the next request is a full `200`, not a reused key.
- `a_revoking_304_never_serves_new_headers_to_a_lock_waiter` — an owner
  revalidates while a second client waits on the cache lock; neither receives
  the old body under the revoked headers.
- `a_revoked_304_entry_does_not_resurrect_from_disk` — the revoked entry is
  absent from disk and the clean replacement reloads after a restart.
- `a_second_304_to_the_unconditional_retry_is_a_bad_gateway` — an origin that
  answers `304` even to the unconditional retry produces `502`, not a
  forwarded `304`.

The existing cache journeys (hit/miss, `Vary`, clean `ETag` revalidation,
TTL, single-flight, disk restart, authorization/range bypass, oversized
bodies, pipelining) remain in the same 20-test binary.

The unit test
`cache::tests::a_304_that_revokes_shared_storability_is_not_refreshable`
covers the policy matrix directly (`Set-Cookie`, `private`, `no-store`,
changed value, `Vary: *`, session `Vary`).
