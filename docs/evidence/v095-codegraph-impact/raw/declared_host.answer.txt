## Direct answer

`declared_host` is only consumed by one production function: `resolve_with` in `eqproxy-cli/src/main.rs:2844-3382`. Changing it therefore cannot break request routing at runtime — it breaks **configuration resolution**, i.e. startup (`run`), `config validate`, `config apply`, `config rollback`, `plan`, `explain`, `doctor`, plus the admin-API apply/reload path (`apply_candidate` / `handle` / `reload`). All of these reach it through the same three entry calls (`gate`, `resolve`, `apply_candidate`).

## What specifically breaks per change

- **Return type or `Option` semantics changed** (e.g. returning the first host instead of `None` for mixed pools): only `resolve_with` will fail to compile/behave, and the effect is the upstream TLS `server_name` default — certificates get verified against the declared name versus the resolver's address (IP SAN). Wrong output there means upstream TLS verification failures at connection time, not at config time. The five schema tests at `schema.rs:1599-1622` pin exactly this behavior.
- **Erroring or panicking inside `declared_host`**: `resolve_with` returns `Err`, which surfaces as `"inconsistent configuration after validation: …"` in `gate` (`main.rs:~375`, `~430`), `apply_candidate` (`main.rs:~2610`), `plan` (`main.rs:839`), `rollback` (`main.rs:1362`), `explain` (`main.rs:799`), `doctor` (`main.rs:1577`) — i.e. the process refuses to start and `config validate/apply/plan/explain/doctor` exit non-zero, while admin applies return `ApplyReply::Invalid`.

## Caveats on the graph

Also, `declared_host`'s recorded outgoing edge to `starts_with_ignore_ascii_case` (`eqproxy-core/src/rules.rs`) does not match the `eq_ignore_ascii_case` used in the visible body.

Recommendation: keep the signature and the "all entries agree or `None`" semantics stable, since nine CLI/admin entry points funnel through `resolve_with`; if you must change it, the only production edit site is `main.rs:2844-3382` and the schema tests at `schema.rs:1595-1623` are the safety net to update.
